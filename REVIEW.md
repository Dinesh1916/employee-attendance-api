# REVIEW.md

Defects found in the starter `app/main.py` (helpers and endpoints).

| # | Where (function / line) | What is wrong | How you'd notice it (test, input, or symptom) | How I fixed it |
|---|---|---|---|---|
| 1 | `compute_late_minutes` | Computes `(punch_in - start)` where `start` is built by replacing fields on a naive `punch_in` datetime **with no timezone**, then divides by 60 and checks `> 10`. Two bugs: (a) it returns `minutes if minutes > 10 else 0` — but R2 says *strictly more than 10 minutes* means late; 10 min exactly should return 0, not 10. (b) `start` is built via `punch_in.replace(hour=h, minute=m, …)` — if `punch_in` is UTC-aware, `start` becomes a same-timezone instant but on the wrong wall-clock day (e.g., a 09:28 IST punch-in is 03:58 UTC; `.replace(hour=9, minute=30)` makes 03:30 UTC on the same UTC date, not 04:00 UTC = 09:30 IST). | A punch-in at exactly 09:40 IST would be returned as 10 late minutes (wrong — should be 0). Any non-UTC punch-in would produce wrong late_minutes. | Build shift_start on the IST attendance date explicitly: `datetime(att.year, att.month, att.day, h, m, tzinfo=IST)`. Return 0 when `elapsed_mins <= 10`, else `math.floor(elapsed_mins)`. |
| 2 | `compute_overtime` | `datetime.fromisoformat(date_str)` returns a **naive** datetime; adding `.replace(hour=h, minute=m, tzinfo=IST)` then comparing with a UTC-aware `punch_out` raises `TypeError` in Python 3.x. Also, there is no 30-minute minimum (R3 says only count if >= 30 min). | Any call to punch-out raises `TypeError: can't subtract offset-naive and offset-aware datetimes`. | Build `end_ist` as a timezone-aware IST datetime on the correct calendar day (with overnight shift handling), then apply the `>= 30` guard before returning. |
| 3 | `compute_work_hours` | Uses `round(…, 2)` which is Python's banker's rounding (round-half-to-even). R4 requires *half-up* rounding. E.g., `round(3.125, 2)` gives `3.12` in Python but R4 requires `3.13`. | A session lasting exactly 3 hours 7.5 minutes would produce 3.12 instead of 3.13. | Implement `round_half_up` as `math.floor(value * 100 + 0.5) / 100`. |
| 4 | `health` (GET /health) | Just returns `{"status": "ok"}` unconditionally — never pings MongoDB. The spec says "Returns 200 only if MongoDB answers a ping, otherwise 503." | Stopping MongoDB then hitting `/health` still returns 200; the runner pre-flight check passes even when the DB is down. | `db.command("ping")` in a try/except; raise `HTTPException(503)` on failure. |
| 5 | `create_employee` | Uses `find_one + insert_one` (check-then-insert). Concurrent requests for the same `emp_code` can both pass the `find_one` check and both succeed — violating the uniqueness requirement. Also, `created_at` is set as a naive datetime (`datetime.now()` with no timezone). | Two simultaneous POST /employees with the same emp_code both return 201. | Rely solely on the unique index and catch `DuplicateKeyError`; use `datetime.now(tz=timezone.utc)`. |
| 6 | `list_employees` | (a) `skip = page * page_size` — should be `(page - 1) * page_size`; `page=1` would skip the first page. (b) `total = db.employees.count_documents({})` ignores the `department` filter — total should count the filtered set. (c) No `sort` applied (R10 says sorted by `emp_code` ascending). | Page 1 returns items starting from index 20 (second page). Filtering by department shows wrong total. | Use `(page - 1) * page_size`, filter total query with `q`, and add `.sort("emp_code", ASCENDING)`. |
| 7 | `punch_in` (POST /attendance/punch-in) | (a) `datetime.fromtimestamp(ms/1000)` without `tz=` produces a naive local-time datetime — on a server in UTC this silently loses the IST offset, producing the wrong attendance date for IST edge times. (b) `datetime.now()` (no tz) same issue. (c) Uses check-then-insert (`find_one` before `insert_one`), not concurrency-safe. (d) No validation that the employee exists before deriving the date — `emp` could be `None`, causing `emp["shift_start"]` to raise `TypeError`. (e) Ignores R1 overnight shift logic for attendance date. (f) Returns a stray `"id"` field that is not in the OpenAPI schema. | Punch-in at 00:15 IST (18:45 UTC previous day) assigned to wrong date. Concurrent punch-ins both succeed. | Use `millis_to_dt()` (UTC-aware, truncated), check employee first, use `insert_one` inside try/except `DuplicateKeyError`, implement overnight date logic, remove `"id"` from response. |
| 8 | `list_attendance` | Loads the **entire** collection into memory with `list(db.attendance_logs.find(q))`, then sorts and slices in Python. On 100k records this is ~100 MB of data per request and O(N log N) in application memory. The spec says it "must stay fast on a collection of ~100,000 records; do not load the collection into memory." Also `total = len(docs)` is measured after loading everything. | Under load with 100k rows this will exhaust memory and time out. | Push sort, skip, and limit to MongoDB; use `count_documents(q)` for total. |

## Things I looked at and decided were NOT defects

- **`MONGO_URI` / `MONGO_DB` defaults** — `mongodb://localhost:27017` and `attendance_db` are reasonable local defaults; the spec says real env vars win, which `dotenv` + `os.getenv` handles correctly.
- **`body.model_dump()` in `create_employee`** — valid Pydantic v2 API; not a bug.
- **`from dotenv import load_dotenv` / `load_dotenv()` at module level** — acceptable for the assignment's local development setup.
